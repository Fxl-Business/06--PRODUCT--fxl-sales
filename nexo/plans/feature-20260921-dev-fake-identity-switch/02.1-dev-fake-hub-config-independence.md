# 02.1 - dev-fake must not need the Hub to boot

## Why this slice exists, measured rather than supposed

At the wave 2 boundary the orchestrator booted the API with `SALES_AUTH_FAKE=1` and nothing
listening on `localhost:9016`, because acceptance 1 has no automated oracle.
It did not boot:

```
HubConfigError: hub-sdk: FXL_HUB_CONFIG.environment must be exactly one of
"production", "staging" or "development".
  at apps/api/src/middleware/app-auth.ts:96   (module top level)
  at async installFakeAuthIfRequested (apps/api/src/auth/select.ts:237)
  at async apps/api/src/server.ts:47
```

The cause was isolated, not guessed: the identical probe with `FXL_HUB_API_URL` blanked boots in two
seconds, prints the roster banner and answers `200` on `/health` and on
`/api/v1/sales-ops/bootstrap`.

This machine's `apps/api/.env` has `FXL_HUB_API_URL` set and the other four identity variables
empty. `CLAUDE.md` records that a PARTIAL discrete configuration is a boot failure by deliberate
design since v3.1.0, and that design is CORRECT and is not being changed here.

The defect is narrower and it is ours. The development identity mode exists so the product can run
WITHOUT the Hub, and it currently cannot survive a leftover Hub variable, because
`apps/api/src/middleware/app-auth.ts` resolves the Hub configuration at its own module top level and
that module is imported during boot no matter what, since the sales-ops router depends on
`appAuthMiddleware`.

## The shape of the fix

`app-auth.ts` line 96 is `const hubSdkConfig: HubConfig | null = tryLoadHubAuthConfig(hubEnvBag(env));`.

When, and ONLY when, the development identity flag is active and the process is not production, a
`HubConfigError` from that call resolves to `null` instead of aborting the boot, and the API prints
one clear line saying the Hub configuration was ignored because development identities are active.

`null` is already a state this module understands: it is what a machine with no credentials at all
produces, and it is what keeps `503 hub_auth_not_configured` alive. Under the development adapter
the value is irrelevant anyway, because the adapter REPLACES the middleware and the BFF is already
documented as unusable in this mode.

Three things are deliberately NOT done.
The catch is not blanket: `CLAUDE.md` states there is no blanket `try/catch` in `auth-provider.ts`
and that a bad Hub configuration is a boot failure, and that stays true for every run without the
flag.
The catch does not widen to other error types; only the SDK's own configuration error is absorbed.
`auth-provider.ts` is not touched at all, so the one resolver keeps its single behaviour and this
slice's tolerance lives at the one call site that can know the flag is on.

## Oracles

Both live in `apps/api/src/auth/__tests__/dev-identity-hub-config-independence.test.ts`.

1. `boots and installs the adapter when the Hub configuration is partial and the flag is set` -
   the flag on, a deliberately partial Hub env bag, and the assertion that no throw escapes and the
   adapter is installed and serves a request.
2. `still fails the boot on a partial Hub configuration when the flag is absent` - THE DECISIVE ONE.
   The same partial configuration with the flag unset must still throw, and the test asserts the
   throw. Without this test the fix could silently become a blanket tolerance and nothing in the
   suite would notice, which is the exact failure mode `CLAUDE.md` warns about.
3. A production case: flag set plus `NODE_ENV=production` still refuses, so the tolerance cannot
   become a production escape hatch.

## Handoff to slice 07

`CLAUDE.md` must record this conditional tolerance where it currently states that a bad Hub
configuration is always a boot failure. The statement stays true for the real path and now needs the
scope written down, in the same way the ONE-gate sentence is being qualified.
