# 07.1 Seller own-lead defaults

Inserted during Execute (replan 2) after the slice 07 browser walk.

## Findings (measured in the browser walk)

1. As `leads-seller`, `Novo lead` with no vendedor chosen answers `403 seller_scope`, because `insertLead` requires a seller to name themselves (`requestedSeller !== gate.sellerPersonId`).
   The dialog then closes and the typed input is lost, with only a generic "Não foi possível salvar o lead".
2. The move dialog shows "Escolha a posição na coluna." in red before any interaction (both editions).
3. The contact dialog's vendedor picker and close button have no accessible name.

## Decisions (HOW, recorded for the Report)

- D-07.1a. The default applies ONLY to the leads-edition create (`createContactLead`): when the caller is a scoped seller (`gate.sellerPersonId` set) and the body carries no `sellerPersonId` (absent or null), the lead is assigned to `gate.sellerPersonId`.
  An explicit different id still answers `403 seller_scope`.
  The full edition (`createLead`) keeps today's rule byte-for-byte, so FXL is unchanged.
  Implement as an option on the private `insertLead` (for example `{ defaultSellerToCaller: true }`) passed only by `createContactLead`; do not change `createLead`'s call.
- D-07.1b. In the leads edition, when the viewer is not an admin, `ContactLeadDialog` does not render the Vendedor field and the payload omits `sellerPersonId` on create (on edit it keeps the stored value untouched by omitting the key).
  The container passes the role decision down as a prop (`showSellerPicker`), reading roles the same way it already does.
- D-07.1c. Save failures in the contact dialog keep the dialog open, keep every typed value, and show the mapped error inline inside the dialog (reuse the existing save-error copy helper in `contact-lead.ts`); the dialog closes only on success.
- D-07.1d. The move dialog's position validation message renders only after the user changes a field or presses confirm.
  This is a small bug fix that also applies to the full edition; it must not change any other move behaviour (the `MoveLeadPayload` emitter stays the one emitter).
  If the move dialog file has a different name, find it via `data-move-trigger` and adjust files_modified in the commit message.
- D-07.1e. Give the contact dialog's vendedor Combobox and close button accessible names (`aria-label="Vendedor responsável"`, `aria-label="Fechar"`), matching how other dialogs in the app label them.

## Tests (Red first)

- API integration (`test/rls/leads-edition.test.ts`): a scoped seller creates a contact lead with no `sellerPersonId` and gets it assigned to themselves; with `sellerPersonId: null` same; with another vendedor's id gets `seller_scope`; an admin with no `sellerPersonId` creates an unassigned lead; the full-edition `createLead` by a seller with no seller still answers `seller_scope` (FXL oracle).
- Web: dialog hides Vendedor for non-admin and shows it for admin; create payload for non-admin has no `sellerPersonId` key; a rejected save keeps the dialog open with values and inline error; move dialog shows no error before interaction and shows it after an invalid confirm; accessible names present.

- Update `nexo/knowledge/reference/kanban-de-leads.md` with the D-07.1a and D-07.1b rules.
