# An optimistic row is visible but never actionable

## Goal

Slice 01 exported `isOptimisticId` and never called it, leaving a client-side placeholder id reachable by the UI.
This slice wires that guard so a row whose create POST is still in flight can be seen but not acted on: its edit affordance is rendered disabled with the pt-BR label `Salvando...`, and one new pure function keeps optimistic rows out of every picker whose selected id ends up in a request body.
It also closes the second Verify finding by adding an integration test that asserts on the id a *subsequent* request carries, which is the only observation that can distinguish "the `onSuccess` reconcile ran" from "the refetch happened to overwrite the snapshot".

## Current state

### The invariant slice 01 left unstated

Three sales-ops cadastros write optimistically: áreas, clientes, pessoas.
The inserted row's id is a client-side placeholder built by `optimisticId` at `apps/web/src/sales-ops/optimistic.ts:39-41`, of the shape `optimistic:<collection>:<name>`.
`isOptimisticId` is defined at `apps/web/src/sales-ops/optimistic.ts:35-37` and, outside `apps/web/src/sales-ops/__tests__/optimistic.test.ts`, has zero callers.
A repo-wide grep for `isOptimisticId` in `apps/web/src` returns only `optimistic.ts` and that one test file.

The placeholder is replaced by server truth in `useOptimisticBootstrapWrite.onSuccess` at `apps/web/src/sales-ops/hooks.ts:98-112`, which calls `reconcileOptimisticRow`.
Until that fires, the placeholder is live in the query cache and therefore live in every component that reads `bootstrap`.

## Decision

**Chosen treatment: the row stays visible and its edit affordance renders disabled, labelled `Salvando...`, and every picker that feeds an id into a request body stops offering the row at all.**

The invariant, stated once so a future reader can check it in one pass: *an optimistic row is visible in the cadastro list that created it, and nowhere else. It is never selectable and never editable.*

### Why disabled, and not the two alternatives

**Hide the edit affordance.** Rejected. The row appears, its action column is blank, then a button materialises a beat later. That is a layout that moves under the operator's cursor and reads as a rendering bug, not as "still saving". It also destroys the affordance's own affordance: nothing on screen explains why the row cannot be edited.

**Let it open and block the save.** Rejected, and it is the worst of the three. The operator opens the dialog, retypes a corrected name, presses `Salvar`, and the app either silently swallows it or throws. The whole point of the optimistic write is that the operator's work is never lost, and this option loses work at the exact moment the operator is trying to correct a typo. It also puts the guard behind a decision the operator has already committed to, which is the latest possible place to say no.

**Disabled, with a label.** Chosen. The row is where the operator expects it, the action is where the operator expects it, and it is visibly not yet available. The dimming plus the tooltip answer "why" before the click rather than after, which is the whole difference between a guard and a rejection. It is also honest about what is happening: the row genuinely is mid-save, and the disabled state lasts exactly one POST round trip. It matches the disclosure idiom slice 01 already introduced for the same window, the header's `Atualizando` spinner.

### pt-BR affordance text

`title="Salvando..."` on the disabled button, and `aria-label={`Salvando ${row label}`}`.
The enabled state keeps `title="Editar"` and gains `aria-label={`Editar ${row label}`}` on áreas and clientes, matching the convention `PeopleView` already uses at `apps/web/src/sales-ops/SalesOpsApp.tsx:1889`.
Three dots, not the ellipsis character, matching the existing `Buscar ou digitar um novo cliente...` placeholder.

No extra text node is added to the row.
A `Salvando...` badge that appears and disappears inside one round trip is noise, and the dimmed disabled control plus its tooltip already carry the whole message.

### Why the pickers are fixed here rather than deferred

The reported defect and sites #4 through #9 are one defect with one cause: a placeholder id is indistinguishable from a real one to every consumer of `bootstrap`.
Fixing only the reported instance ships a slice that names the class and then leaves five reachable members of it in place, including two that lose an entire wizard's typing.
The cheapest complete fix is not a per-picker audit but one seam: a pure `withoutOptimisticRows(snapshot)` in `optimistic.ts`, memoised once in `SalesOpsApp`, handed to every consumer except the three cadastros list views.
That is one new function and a set of identifier swaps, it is provably complete for `ProductDialog` and `SaleWizardDialog` because those two receive nothing else, and it needs no follow-up when a new picker is added.
The function returns its input by reference when nothing is optimistic, which is the normal case, so it adds no render churn.

   ```ts
   export function withoutOptimisticRows(snapshot: SalesOpsBootstrap): SalesOpsBootstrap {
     const areas = snapshot.areas.filter((row) => !isOptimisticId(row.id));
     const clients = snapshot.clients.filter((row) => !isOptimisticId(row.id));
     const people = snapshot.people.filter((row) => !isOptimisticId(row.id));
     if (
       areas.length === snapshot.areas.length &&
       clients.length === snapshot.clients.length &&
       people.length === snapshot.people.length
     ) {
       return snapshot;
     }
     return { ...snapshot, areas, clients, people };
   }
   ```

## Risks

- **`disabled` and synthetic clicks.** Tests 2 and 5 depend on React not invoking `onClick` for a `disabled` `<button>`, which `react-dom`'s `shouldPreventMouseEvent` guarantees independently of whether happy-dom filters `dispatchEvent`. If that assumption were wrong the tests would fail loudly rather than pass vacuously, so the risk is a red test, not a false green.
- **Nav-label coupling in test 8.** The test clicks a sidebar button matched on the literal text `Produtos` from `apps/web/src/sales-ops/navigation.ts:59`, and batch slice 10 renames that screen to "Produtos & Serviços". The test will break at that rename. Accepted: it breaks visibly, in one place, and slice 10 has to touch the label anyway. The alternative, matching on a substring, would silently match the wrong control.
- **`persistedBootstrap` identity churn.** Mitigated by the reference-preserving early return in step 1. If it were dropped, every bootstrap render would hand `SaleWizardDialog` a fresh `bootstrap` prop; that no longer remounts the wizard body since slice 01 simplified its `key`, but it would still recompute `buildDashboardModel` on every render, which is the exact regression slice 01 fixed. Do not drop the early return.
- **The wizard `Cadastro incompleto` flash.** Documented in step 6 and accepted as correct. Worst case is one round trip of an accurate message.
- **The guard hides a stuck row.** If a create POST never settles, the row stays visibly uneditable indefinitely. That is strictly better than today, where it stays editable and every edit 500s, and TanStack's `retry: 1` plus the eventual `onError` rollback bound the window in practice.
- **Placeholder ids can still be constructed elsewhere.** `withoutOptimisticRows` is a discipline, not an enforcement: a future component that reads `bootstrap` directly reintroduces the hole. Slice 01 had the same shape of residual risk and answered it with an ESLint rule. Not worth a rule for one snapshot object; the docblock plus the single memo is the mitigation, and the Refactor grep is the check.
- **Atomicity.** One commit. The three affordance guards, the picker seam and the tests are one behavioural change with one invariant, and splitting them would ship a slice that names the class while leaving members of it live.
