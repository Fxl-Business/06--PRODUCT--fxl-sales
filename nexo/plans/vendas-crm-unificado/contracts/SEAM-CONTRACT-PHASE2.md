# SEAM CONTRACT - phase 2 API and web (orchestrator)

Authoritative for the phase 2, 3 and 4 planners, on top of `contracts/SEAM-CONTRACT.md` (tables, constants, services from slices 05a, 05b, 06).
The API planner of phase 2 finalizes the exact zod schemas and wire types in its plans and must keep every name below; a deviation it cannot avoid is written in its result summary and reconciled by the orchestrator at plan-check.
All routes live under the existing `/api/v1/sales-ops` router, behind the existing access gate, org from `c.get('orgId')` only, seller scope through the one server predicate (port of `leadSellerCondition`) and `liveLeadCondition`.

## Cutover (API, code only)

- After phase 2 every lead read and write uses the NEW tables (`sales_ops_crm_leads` and friends) and the pipeline stages; nothing writes `sales_ops_leads`, `sales_ops_lead_products` or `sales_ops_lead_stages` anymore, and they stay byte-intact as the frozen pre-cutover copy.
- Migration `0031_crm_cutover_resync` repeats `0030_crm_legacy_copy.sql` verbatim (idempotent copy with the same uuids) so rows written to the old tables after 0030 are not lost.
- Existing routes keep their paths and their response shapes (additive fields only), so today's web keeps working while the web slices land: `GET/POST /leads`, `GET /leads/summary`, `GET /leads/deleted`, `GET/PATCH /leads/:id`, `POST /leads/:id/move`, `POST /leads/:id/delete`, `POST /leads/:id/restore`, `GET /lead-stages`, `POST /lead-stages`, `PATCH /lead-stages/:id`, `POST /lead-stages/reorder`, the import routes, and the lead conversion through `POST /sales` (which sets the lead's `sale_id`).
- `GET /lead-stages` returns the stages of the org's DEFAULT pipeline (or of `?pipelineId=`), each with the legacy `kind` derived as: `type = 'orcamento'` -> `'conversion'`; `exit_kind = 'perdido'` -> `'lost'`; everything else -> `'normal'`; plus the additive fields `pipelineId`, `type`, `behavior`, `exitKind`, `requiresReason`.
- `ensureCrmDefaultsForOrg` is called where `ensureLeadStagesForOrg` is called today (bootstrap, `GET /lead-stages`) and by `GET /pipelines`; registered in `crm-seed-callers.test.ts`.
- One lock order: every writer of `stage_id`/`position` on `sales_ops_crm_leads` takes the per-org board advisory lock first (same key as `lockLeadBoard`).
- The two write contracts (`full` and `contact`) collapse into ONE lead schema (`LeadWriteSchema`): `contactName` required, a contact (`contactPhone` or `contactEmail`, at least one) required, everything else optional: `pipelineId`, `stageId`, `sellerPersonId`, `clientId` or `clientName` (inline create stays a separate `POST /clients`), `estimatedValueBrl`, `fields` (dynamic values). `leadFieldSet` and the edition no longer choose a schema. Old payload keys (`description`, `contactBirthDate`, `products`) are still accepted and mapped onto their field definitions (`descricao`, `nascimento`, `produtos`) so today's web keeps working.
  Note for the planner: today the contact is optional; the request makes "nome e contato" the only required fields, so the new rule is at least one of phone or e-mail. Existing rows without contact stay valid (the rule applies to writes that touch the contact or create a lead).

## Lead wire shape (additive)

`SalesOpsLead` keeps every current field and adds `pipelineId: string`, `stageType: 'normal' | 'orcamento' | 'saida'`, `stageExitKind: 'ganho' | 'perdido' | 'pausado' | null`, `fields: LeadFieldValue[]` where `LeadFieldValue = { fieldId: string; key: string; value: string | number | null | Array<{ id: string | null; name: string }> }` (money in integer cents, date as ISO civil day, option as option key, references as `{id, name}` items).
`description`, `contactBirthDate`, `products` keep being projected from the `descricao`, `nascimento`, `produtos` field values.

## New routes

- `GET /pipelines` -> `{ pipelines: Array<{ id, name, isDefault, position, status, stages: Array<{ id, name, position, type, behavior, exitKind, requiresReason, status }>, transitions: Array<{ fromStageId, toStageId }> }> }`, active ones, ordered by position.
- `GET /field-definitions` -> `{ fields: Array<{ id, key, label, kind, referenceTarget, multiple, options, filterable, isSystem, removable, position }> }` (active). No create/edit of definitions in this run (onboarding is out of scope); the Cliente system field is always present and can never be removed (a write that omits or clears the Cliente DEFINITION does not exist; a lead may still have no cliente value).
- `GET /leads/:id/summary` -> `{ lead: SalesOpsLead, pipeline: { id, name }, stage: { id, name, type, exitKind }, nextStages: Array<{ id, name, type, exitKind, requiresReason }>, timeline: Array<{ kind: 'stage_changed' | 'note' | 'followup', at, actorName, fromStageName?, toStageName?, reason?, body?, nextStep?, dueOn?, doneAt? }>, followups: Array<{ id, nextStep, dueOn, ownerName, doneAt }> }`. `nextStages` lists ONLY the stages allowed by `sales_ops_pipeline_transitions` from the current stage.
- `POST /leads/:id/advance` body `{ toStageId, nextStep?, dueOn?, note?, reason? }`:
  - `409 { error: 'transition_not_allowed' }` when the pair is not in the transitions table (also when the stage belongs to another pipeline);
  - `400 { error: 'validation_error', reason: 'followup_required' }` when the destination is NOT an exit stage and `nextStep` or `dueOn` is missing (a follow-up is mandatory with a date); exits (`saida`) do not require one;
  - `400 ... reason: 'reason_required'` when the destination `requires_reason` and `reason` is empty;
  - writes, in ONE transaction after the board lock: the stage move (position at the end of the destination column, `stage_changed_at = now()`), exactly one `sales_ops_crm_lead_events` row (`stage_changed`, from, to, reason, actor name from the token), the note (linked to the event) when given, and the follow-up when given;
  - a destination of type `orcamento` with behaviour `opens_orcamentos` answers `409 { error: 'sale_required_for_conversion' }` exactly like today's move, because the proposta wizard owns that conversion (unchanged flow through `POST /sales`).
- `POST /leads/:id/move` (drag) enforces the same transition graph for a cross-stage move (`409 transition_not_allowed`) and writes the same history event; a reorder inside one column writes no event and never moves `stage_changed_at`.
- `POST /leads/:id/notes` `{ body }` -> 201; `GET /followups?scope=mine|team&from=YYYY-MM-DD&to=YYYY-MM-DD&status=open|done|all` (team needs admin; mine = owner is the caller's pessoa or created by the caller); `POST /leads/:id/followups` `{ nextStep, dueOn, ownerPersonId? }`; `POST /followups/:id/done`.
- Period filter on every list: `from`/`to` ISO civil days interpreted in `America/Sao_Paulo` (inclusive), validated with `isIsoDay`; leads filter on `created_at`, follow-ups on `due_on`, propostas on their existing date semantics (created for open ones, `won_at` for won ones). Shared helper converts a civil-day range into `[from 00:00 -03:00, to+1 00:00 -03:00)` through `@fxl-sales/shared-utils/sao-paulo-day`; never `new Date().toISOString().slice(0, 10)`.
- `GET /leads` and `GET /leads/summary` accept `pipelineId` (default: the org's default pipeline), `from`, `to`, and dynamic filters `f.<fieldKey>=<value>` for `filterable` fields only (cliente by id, options by key, text by case-insensitive contains, number/money/date by `min`/`max` as `f.<key>.min`); an unknown or non-filterable key is `400`.

## Web (consumes the routes above; no edition branch for these features)

- ONE lead component `LeadForm` in `apps/web/src/sales-ops/leads/` replaces `LeadDialog` and the contact dialog: name and contact required; empresa picker creates a cliente inline in BOTH editions (`onCreateClient` seam, copy `Buscar ou criar novo cliente`); choosing an empresa prefills the contact (`sales_ops_clients.contact`) and the responsible seller when the cliente has one; dynamic fields rendered by kind from `GET /field-definitions`; the Cliente field cannot be removed from the form.
- Lead summary page route: `operacional/leads/:leadId` and `meus-dados/leads/:leadId` (the third segment of the existing pattern; today `leads` uses it for a stage id: the planner must move the stage-in-URL to a query string or keep both unambiguous and say how); clicking a card or a Lista row opens the SUMMARY, never the form; the summary has `Editar` (opens `LeadForm`), `Avançar` (a dialog listing only `nextStages`, asking próximo passo + data unless the destination is an exit), notes, and the timeline.
- Follow-ups list: a new view (for example `operacional/follow-ups` and `meus-dados/follow-ups`) with Minha/Equipe and the period filter.
- Kanban: a pipeline selector (component state or query string, not a new path segment), columns from `GET /pipelines`, colours and behaviour keyed on `type`/`exitKind` (no `kind ===` inline, the write-surface guard stays green), the period filter, and the existing drag still going through `MoveLeadDialog` as the one emitter.
- Proposta versus Vendido decided by stage type (`orcamento` versus exit `ganho`) on the lead side and by `status` on the proposta side; each Propostas submenu entry gets its own route under the existing pattern.
- Every list (Propostas, Prospecção Lista and Quadro, Follow-ups, Clientes where it has dates) has the period filter, São Paulo civil days.
