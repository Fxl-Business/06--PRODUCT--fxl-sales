# 07a - API cut-over to the unified CRM tables (phase 2)

## Parts, execute in order

Why parts: the cut-over changes about 1,900 lines in 51 files and CANNOT be cut by area. The etapas and the leads reference each other (`sales_ops_crm_leads` has a composite FK onto `sales_ops_pipeline_stages`), the import creates both, and every lead test fixture creates etapas, so moving the stage side without the lead side (or the reverse) leaves a tree where new etapas cannot hold old leads. The parts below are the independently green cuts that DO exist:

1. `parts/07a1-cutover-fundacao.md` - migration 0031 (resync), the pure and DB helpers under `apps/api/src/domains/crm/`, `deleteCrmForOrgs`. Additive only: nothing is wired. Focused: `pnpm --filter @fxl-sales/api exec env VITEST_INTEGRATION=1 vitest run test/rls/crm-cutover-resync.test.ts`.
2. `parts/07a2-cutover-servicos-rotas-import.md` - the atomic cut-over: write schema, lead service, trash service, etapa service and routes, seed facade, import, and every test fixture. Focused: `pnpm --filter @fxl-sales/api exec env VITEST_INTEGRATION=1 vitest run test/rls/crm-cutover-frozen-tables.test.ts test/rls/crm-lead-write-fields.test.ts` and `pnpm --filter @fxl-sales/api exec vitest run src/domains/crm src/domains/sales-ops/leads`.
3. `parts/07a3-cutover-seed-dev.md` - the dev seed writes the unified tables through a pure adapter. Focused: `pnpm --filter @fxl-sales/api exec vitest run scripts/__tests__/crm-seed-rows.test.ts scripts/__tests__/seed-plan.test.ts`.

Verified on the prototype: after part 3 the whole API unit suite is 1,551 tests green and the whole integration suite is 503 tests green (one local Postgres, serial). Parts 1 and 3 are each green on their own (part 1 adds files only; part 3 only replaces the dev seed inserts).

## Design (decisions already made)

1. NOTHING writes `sales_ops_leads`, `sales_ops_lead_products`, `sales_ops_lead_stages` after this slice. `schema.ts` keeps their definitions (the migrations and the frozen-copy tests need them); no product source file names them (`frozen-lead-tables.test.ts` scans `apps/api/src`). The dev seed script still DELETES old rows of the local database (a proposta delete is restricted by an old lead's `sale_id`), and never inserts into them.
2. Migration `0031_crm_cutover_resync` is a RESYNC, not only a repeat. Part A repeats `0030` byte for byte (copies rows the old tables received after 0030). Part B overwrites a stale copy with the row the old table changed LAST, using the rule `COALESCE(old.updated_at,'-infinity') > COALESCE(new.updated_at,'-infinity')` (every old writer stamped `updated_at`; the new code always stamps it, so a row the new code wrote is never overwritten and the whole migration is idempotent): etapas (name, position, status, archived_at; a rename that collides is skipped and converges on a second run), lead columns (etapa, position, `stage_changed_at`, vendedor, empresa, valor, `lost_reason`, `sale_id`, `deleted_*`, contact), one `stage_changed` event (`system`/`Migração`) for every lead whose etapa differs (written BEFORE the lead update), and field values (`descricao`, `nascimento`, `produtos`) by `ON CONFLICT (org_id, lead_id, field_id, position) DO UPDATE`. A value REMOVED in the old table (a produto dropped, a description cleared, a birth date cleared) is NOT mirrored: a migration may not DELETE. The stale value stays until an operator edits the lead. Accepted, documented in the header, pinned by the oracle. 0030 and 0031 ship in the same deploy, so the window is empty in practice.
3. `GET /lead-stages` keeps its row shape: `id, orgId, name, kind, isSystem, position, status, archivedAt, createdAt, updatedAt` plus the additive `pipelineId, type, behavior, exitKind, requiresReason`. `kind` is DERIVED by `legacyStageKind` (`type = 'orcamento'` -> `conversion`, `exit_kind = 'perdido'` -> `lost`, else `normal`, so Ganho and Pausado read as `normal`) and `isSystem` by `legacyStageIsSystem` (`kind <> 'normal'`: the conversion and the lost etapa stay immutable through `PATCH /lead-stages/:id`). It lists the DEFAULT pipeline, or `?pipelineId=` (unknown id: empty list; non-uuid: 400).
4. `stages-seed.ts` stays as a FACADE: `ensureLeadStages(tx, orgId)` and `ensureLeadStagesForOrg(db, orgId)` call `ensureCrmDefaults` and return the default pipeline's etapas in the legacy shape. The callers (bootstrap, import routes, `listLeadStages`) and `stages-seed-callers.test.ts` stay byte-identical; `crm-seed-callers.test.ts` registers `stages-seed.ts`. `LEAD_STAGE_SEEDS` stays exported but is FROZEN (the 0022 parity oracle and the import template tests read it); nothing seeds from it.
5. The default pipeline of a NEW org has seven etapas (Novo, Qualificação, Em negociação, Proposta, Ganho, Perdido, Pausado) and 22 transitions, not the old four. This is the one visible behaviour change of the cut-over; the tests that counted four are listed in affected_tests.
6. `createLeadStage` on an org that never read its etapas creates a BARE default pipeline (`ensureBareDefaultPipeline`, no etapa, no transition) and then the etapa, so "an org that created its own first etapa is never seeded" still holds. A new etapa is always `type normal`, `behavior none`, no exit. It receives the transitions the shared rule gives it (`planPipelineTransitions` filtered to the pairs that involve it); pairs between other etapas are never touched, and a reorder never regenerates the graph (explicit data). `POST /lead-stages` and `POST /lead-stages/reorder` accept an optional `pipelineId` (unknown: 404).
7. ONE lead write schema. `LeadWriteBaseSchema` is the strict shape (`contactName` required; `contactPhone`, `contactEmail`, `pipelineId`, `stageId` (create only), `sellerPersonId`, `clientId`, `clientName`, `estimatedValueBrl`, `fields`, and the legacy keys `description`, `contactBirthDate`, `products`). `LeadWriteSchema` (create) adds the contact rule: at least one of phone or e-mail, issue message `contactPhone or contactEmail is required`. `LeadPatchSchema` is the same shape, every key optional, without `pipelineId`/`stageId`. The HTTP routes use `LeadWriteSchema`; the spreadsheet import uses the BASE schema (a workbook row has no contact column). A PATCH that touches phone or e-mail and would leave neither is `400 contact_required` from the service. `leadFieldSet`, `createContactLead` and `updateContactLead` are gone; the edition only travels inside `LeadScope` (it still gates the leads-edition seller auto-provision until phase 3 replaces it with the org module). The text caps are exported constants (`LEAD_CONTACT_NAME_MAX` 140, `LEAD_CLIENT_NAME_MAX` 200, `LEAD_DESCRIPTION_MAX` 4000).
8. W1: `fields` is `[{fieldId | key, value}]`; `null` clears a field and an omitted field stays untouched. Values: text -> `value_text`; number -> `value_number`; money -> integer cents `value_cents`; date -> `value_date`; options -> the option key; reference -> `[{id, name}]` (`cliente` -> `client_id` + snapshot through the backing column; `produto`/`servico` -> `value_product_id` + server snapshot, or `value_text` for a free item; `venda` -> `value_sale_id`; `contato` -> `value_text`). Errors are the existing 400 body `{error:'validation_error', reason, itemIndex}` with `field_not_found`, `field_invalid`, `field_reference_not_found` (index = the `fields[]` entry). Naming both `clientId` and a Cliente entry is `field_invalid`. The legacy keys are mapped onto the `descricao`, `nascimento`, `produtos` definitions, created on first use with the exact rows 0030 creates (`LEGACY_FIELD_SPECS`); clearing writes nothing when the org never had the definition. `products` projects ordered by snapshot name (the pre-cutover order).
9. Every lead view is additive: `pipelineId`, `stageType`, `stageExitKind`, `fields: LeadFieldValue[]` (one entry per ACTIVE definition, `null` when empty; Cliente comes from the lead columns), and `description`, `contactBirthDate`, `products` keep being projected. The POST and PATCH responses carry `fields` (same `readLeadView`).
