# Roadmap

## Backlog

- fix: losing a Hub session while the app is open and in use destroys unsaved work. `HubProtected`'s auto-login effect calls `login()` the instant `isSignedIn` goes false, and `login()` is `client.login()`, a full `window.location.assign` to the Hub - so a half-filled proposta wizard is gone. `captureReturnTo` restores the ROUTE and has never restored form state. Measured on production: an idle authenticated tab makes ZERO requests over ten minutes and never reloads, so the trigger is the operator RETURNING and something reading an access token whose cache has lapsed. Two parts, both planned in `nexo/plans/feature-20260810-auth-boot-states/04-preserve-work-on-session-loss.md`: render the signed-out state in place for a LIVE loss while keeping cold entry redirecting as it does today, and renew the token at `exp - 60s` while the document is visible so an open tab never drifts into expiry. Do NOT fix it by putting a `401` back on the revalidation ladder - that only delays destroying the form by six seconds.
- feat: persisting in-progress form state across an authentication redirect. Deliberately OUT of scope for the fix above, because once the app stops navigating away unbidden the operator only loses work when they choose to sign in. Revisit if a case appears where the redirect is genuinely unavoidable.

- feat: the auth boot sequence shows NOTHING while it resolves a session, so an operator sees a blank white screen for as long as the revalidation ladder runs (about 6 seconds normally, longer if a redirect loop is involved) and then, on failure, a single generic `Nao foi possivel restabelecer sua sessao` panel that cannot distinguish "you are not signed in" from "your user has no access to this product" from "the workspace you are currently in has no access". The 2026-08-10 outage was diagnosed from `curl`, not from the UI, precisely because of this. Wanted: a visible authenticating indicator instead of the blank screen, and distinct terminal states - not signed in, account not entitled, and workspace not entitled. The last one should list the operator's OTHER workspaces and let them switch, which is cheap because `profileFromToken` already parses `claims.workspaces` and `UserControls` already renders a workspace `Combobox`.
- fix: `apps/web/src/auth/refresh.ts` classifies on status alone and treats every non-401 as `transient`, so a `403` enters the revalidation ladder, retries four times and lands on the generic recovery panel. That is what turned the hub-sdk CSRF-guard misconfiguration into an opaque outage. A `403` from this BFF is never transient - it is a CSRF or entitlement refusal - and should be surfaced as its own permanent, explanatory state rather than retried. Deliberately NOT changed under hotfix pressure in `v2.7.1`, because a 403 emitted by an intermediate proxy genuinely can be transient and the distinction needs the UX above to land with it.
- chore: report the hub-sdk 1.3.x CSRF origin guard upstream. `createHubBff` 403s any POST whose `Origin` differs from the BFF's own origin; `1.2.0` had no such guard and `MIGRATION.md` documents it nowhere, so it silently breaks every consumer whose web app and API are on different hosts. Ask for a `trustedOrigins` option, which would let `apps/api/src/auth/hub-bff-origin.ts` be deleted entirely.
- chore: `trustedOrigins: [env.CORS_ORIGIN]` in `app-auth.ts` is a single origin, which is right today. A preview deployment, a second web host or a custom tenant domain would each need this widened, and the `CORS_ORIGIN` name does not advertise that it is now also a CSRF allowlist. Consider a dedicated `TRUSTED_WEB_ORIGINS` if a second origin ever appears.

- fix: `writeAuditEntry` has a hash-chain race under CONCURRENT writes. Its tail lookup is `SELECT ... ORDER BY id DESC LIMIT 1 FOR UPDATE`, and under READ COMMITTED that does not re-evaluate the LIMIT after unblocking, and locks nothing at all on an empty table. Measured during the v2.4.0 archive feature: 12 concurrent archives left `verifyChain` reporting `{valid:false, brokenAt:2}`, reproduced by a probe calling `writeAuditEntry` directly with none of the new code in the path, against a byte-identical (md5-verified) copy of the function. So it is PRE-EXISTING and not introduced by `feature-20260805-cadastro-archive-history` - but that feature adds four new writers and bulk-archiving is a far more plausible concurrency source than the single money events that existed before, so the exposure is materially higher. Sequential traffic is unaffected and the shipped tests are green. Fix by serializing on a dedicated advisory lock (`pg_advisory_xact_lock`) rather than on the tail row, which also fixes the empty-table case; do NOT paper over it by widening the isolation level.
- fix: `GET /api/v1/admin/audit` returns `entries: rows` verbatim, and `audit_log.id` is a `bigserial` that arrives as a JS `BigInt`, which `JSON.stringify` throws on - so that endpoint currently answers 500 for any non-empty ledger. Pre-existing, surfaced while planning `feature-20260805-cadastro-archive-history` and deliberately left untouched by it (the new org-scoped read projects `String(row.id)` and is unaffected). Fix by projecting the id to a string there too.
- chore: `getAdminDb()`'s pool is `max: 5` and is now the pool the Hub BFF holds across a bounded (5s) Hub round-trip inside a row-lock transaction, alongside the audit router, the history service and the nightly job. A degraded Hub therefore caps that pool at roughly one refresh per second and stalls those other paths, not just auth. Size the pool for peak concurrent REFRESHES, or give the session store its own pool, and set `idle_in_transaction_session_timeout` on the role so a wedged transaction cannot block VACUUM. Not changed in `feature-20260807-hub-sdk-130-session-hardening` slice 01, which only made the hold bounded.
- fix: a TRANSIENT `/auth/refresh` failure (`503 refresh_unavailable`, `502 invalid_refresh_response`) still reads as `Sessão expirada` in the sales-ops bootstrap panel and in `CadastroHistoryPanel`, because the classification stops at the provider. The public token reader is `() => Promise<string | null>` at roughly forty call sites, so `requireToken` throws an undifferentiated `AuthTokenUnavailableError` and `isAuthFailure` cannot tell a dead session from a Hub outage. `apps/web/src/lib/require-token.ts` deliberately imports nothing (`api-client.ts` imports it, so any import back is a cycle), so the fix is not a local edit: it needs either a `reason` on the error threaded from the provider, or a widened reader contract. Scoped out of `feature-20260807-hub-sdk-130-session-hardening` slice 03 with that reasoning; nothing got worse there, the copy was already wrong for this case.
- chore: `hub_bff_sessions.account_id` is provably dead under SDK 1.3.0 and can be dropped in a later migration. `store.create` has exactly one call site in the whole bundle (`dist/server.js:407-413`) and passes three keys, none of them `accountId`; `/auth/refresh` (`:464`) and `/auth/switch` (`:519`) only spread the record back, so nothing can ever populate the column. `feature-20260807-hub-sdk-130-session-hardening` slice 06 left it in place with a comment rather than dropping it, because a column drop is irreversible and buys nothing while the row is one boolean-free `text` NULL. Drop it only after the Hub confirms it will not start populating the field.
