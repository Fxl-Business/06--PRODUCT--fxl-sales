# Roadmap

## Backlog

- fix: a token read still in flight when the operator clicks `Sair` can sign them back in. The read resolves `transient` (correct - the cache generation bump makes it so), which schedules a ladder rung about 500ms AFTER `failSession()` has already cleared everything. If that rung obtains a token before the awaited `client.logout()` lands server-side, `observeToken`'s live-token branch clears the durable logout intent and the protected subtree re-mounts. Measured by the Gate 2 verifier with a probe, and reproduced byte-identically against `master`'s `react.tsx`, so it is PRE-EXISTING and was not introduced by `quick-20260810-preserve-work-on-session-loss`. It is the same shared-machine exposure `SignedOutPanel` exists to close. The narrow fix is a logout generation counter checked in `observeToken`, mirroring how `operationGeneration` already guards `setActive` against a superseded workspace switch.

- feat: persisting in-progress form state across an authentication redirect. Deliberately OUT of scope for `nexo/plans/feature-20260810-auth-boot-states/04-preserve-work-on-session-loss.md`, which shipped the two parts that make it rarely matter: a LIVE session loss now renders the signed-out state in place instead of navigating, and a visible tab renews its token at `exp - 60s`. So the operator only loses work when they CHOOSE to sign in. Revisit if a case appears where the redirect is genuinely unavoidable.
- chore: the live-loss overlay leaves `children` mounted while signed out, so every data hook underneath it keeps failing on `AuthTokenUnavailableError` behind the panel. That is bounded (`retry: 1`, and `requireToken` throws before any fetch) and invisible, but it means the screen under the overlay is in an error state rather than frozen as the operator left it. If a wizard is ever rebuilt to reset its own state on a query error, this becomes load-bearing and the overlay would need to suspend the subtree instead.

- feat: the auth boot sequence shows NOTHING while it resolves a session, so an operator sees a blank white screen for as long as the revalidation ladder runs (about 6 seconds normally, longer if a redirect loop is involved) and then, on failure, a single generic `Nao foi possivel restabelecer sua sessao` panel that cannot distinguish "you are not signed in" from "your user has no access to this product" from "the workspace you are currently in has no access". The 2026-08-10 outage was diagnosed from `curl`, not from the UI, precisely because of this. Wanted: a visible authenticating indicator instead of the blank screen, and distinct terminal states - not signed in, account not entitled, and workspace not entitled. The last one should list the operator's OTHER workspaces and let them switch, which is cheap because `profileFromToken` already parses `claims.workspaces` and `UserControls` already renders a workspace `Combobox`.
- fix: `apps/web/src/auth/refresh.ts` classifies on status alone and treats every non-401 as `transient`, so a `403` enters the revalidation ladder, retries four times and lands on the generic recovery panel. That is what turned the hub-sdk CSRF-guard misconfiguration into an opaque outage. A `403` from this BFF is never transient - it is a CSRF or entitlement refusal - and should be surfaced as its own permanent, explanatory state rather than retried. Deliberately NOT changed under hotfix pressure in `v2.7.1`, because a 403 emitted by an intermediate proxy genuinely can be transient and the distinction needs the UX above to land with it.
- chore: report the hub-sdk 1.3.x CSRF origin guard upstream. `createHubBff` 403s any POST whose `Origin` differs from the BFF's own origin; `1.2.0` had no such guard and `MIGRATION.md` documents it nowhere, so it silently breaks every consumer whose web app and API are on different hosts. Ask for a `trustedOrigins` option, which would let `apps/api/src/auth/hub-bff-origin.ts` be deleted entirely.
- chore: `trustedOrigins: [env.CORS_ORIGIN]` in `app-auth.ts` is a single origin, which is right today. A preview deployment, a second web host or a custom tenant domain would each need this widened, and the `CORS_ORIGIN` name does not advertise that it is now also a CSRF allowlist. Consider a dedicated `TRUSTED_WEB_ORIGINS` if a second origin ever appears.

- fix: `writeAuditEntry` has a hash-chain race under CONCURRENT writes. Its tail lookup is `SELECT ... ORDER BY id DESC LIMIT 1 FOR UPDATE`, and under READ COMMITTED that does not re-evaluate the LIMIT after unblocking, and locks nothing at all on an empty table. Measured during the v2.4.0 archive feature: 12 concurrent archives left `verifyChain` reporting `{valid:false, brokenAt:2}`, reproduced by a probe calling `writeAuditEntry` directly with none of the new code in the path, against a byte-identical (md5-verified) copy of the function. Sequential traffic is unaffected and the shipped tests are green. Fix by serializing on a dedicated advisory lock (`pg_advisory_xact_lock`) rather than on the tail row, which also fixes the empty-table case; do NOT paper over it by widening the isolation level.
