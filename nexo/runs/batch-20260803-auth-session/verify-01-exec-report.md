## What changed, file by file

### New

**`apps/api/src/auth/session-crypto.ts`**
AES-256-GCM sealing.
`deriveSessionKey(ikm)` is HKDF-SHA256 (`salt = 'fxl-sales/hub-bff-session/v1'`, `info = 'aes-256-gcm'`, 32 bytes).
`createSessionSealer(ikm)` throws below 32 characters of input keying material and returns `{seal, open}`.
Sealed format is `v1.<b64url(iv)>.<b64url(authTag)>.<b64url(ciphertext)>` with the row id as AEAD additional data.
`open` returns `null` for every failure mode - bad format, wrong version, wrong length, wrong key, wrong aad, tampered bytes - so callers get exactly one branch.
Module header states that rotating `FXL_HUB_SECRET_KEY` invalidates every stored session.

**`apps/api/src/auth/hub-session-store.ts`**
The hydrate-around-the-handler store.
Exports `SESSION_TTL_MS` (30 days), `LOGIN_TX_TTL_MS` (600_000), `HubSessionScopeError`, `HubSessionStoreUnavailableError`, `HubSessionHydrateInput`, `DurableHubSessionStore`, `createDurableHubSessionStore`, `createHubSessionStore` and `deleteExpiredHubBffSessions`.
`PostgresHubSessionStore` holds the unit of work in an `AsyncLocalStorage`; every interface method is a pure `Map` operation over it and throws `HubSessionScopeError` outside a scope.
`create` mints a 256-bit base64url id; `get` returns a shallow copy and `null` past `expiresAt`; `update` slides the TTL and is a no-op on an unknown id; `delete` pushes its op unconditionally so it is idempotent; `createLogin` seals the verifier and stores `state` in plaintext; `consumeLogin` pushes `login.delete` only when the row was not already removed by the consume-hydrate.
`#hydrate` reads the one session row under `AND expires_at > now()` and, only when `consumeLoginTx`, runs `DELETE ... WHERE id = $1 AND expires_at > now() RETURNING *`; any database error is rethrown as `HubSessionStoreUnavailableError`.
`#flush` replays the ops in order inside one `db.transaction`, logs `[hub-session-store] flush failed` and swallows.
`withRequest` hydrates before the `try` so a hydrate failure skips both the handler and the flush.
`createHubSessionStore` returns the durable branch when `databaseUrlPresent`, throws in production otherwise, and falls back to `InMemoryHubSessionStore` with a warning in dev.

**`apps/api/src/auth/hub-session-scope.ts`**
`SESSION_COOKIE` / `SESSION_COOKIE_SECURE` / `LOGIN_TX_COOKIE` mirroring `@fxl-business/hub-sdk@1.2.0 dist/server.js:271-273` (verified against the installed dist), `hubSessionCookieName(secureCookies)`, and `createHubSessionScopeMiddleware`.

## Deviations and notes

1. **`getAdminDb()` in the durable branch is called inside the factory, not through a thunk.**
   The plan says the durable branch "calls `getAdminDb()` lazily so that constructing the store never forces a connection at import time." `createDurableHubSessionStore`'s signature in the plan takes `db: NodeDb` directly, so a thunk would have required changing the specified signature. The stated property still holds: `getAdminDb()` is reached only from inside `createHubSessionStore` (never at module import), and postgres-js builds its pool without opening a socket until the first query. The comment in the code says exactly this rather than the word "lazily".

## Blocker A - a blank `HUB_SESSION_ENCRYPTION_KEY` stopped the API booting

`apps/api/src/middleware/app-auth.ts` read `process.env.HUB_SESSION_ENCRYPTION_KEY ?? hubAuthConfig.secretKey`.
`??` does not catch `''`, and this slice ships `HUB_SESSION_ENCRYPTION_KEY=` (blank) in `.env.dev.example`, which `CLAUDE.md` documents as the file an operator copies to `.env`.
So the default local setup reached `createSessionSealer('')`, which throws its 32-character floor, and `server.ts` calls `createAppAuthBff()` at module top level.

Fix: read the validated env object, whose `emptyToUndefined` coercion this slice already added and then did not use.

```ts
encryptionIkm: env.HUB_SESSION_ENCRYPTION_KEY ?? hubAuthConfig.secretKey,
```

A comment above the line records why `process.env` is the wrong source here, so the `??` cannot be re-introduced by someone who reads only the expression.

Regression pin: `apps/api/src/middleware/__tests__/app-auth-bff-wiring.test.ts` loads the whole module graph with `HUB_SESSION_ENCRYPTION_KEY=''` stubbed - the exact shipped value - and calls the real `createAppAuthBff()`.
It asserts the ikm handed to `createHubSessionStore` is `FXL_HUB_SECRET_KEY`, i.e. the blank override read as unset and the documented HKDF default applied.

## Blocker B - `session-crypto.test.ts > refuses a tampered ciphertext` was ~25% flaky

Root cause confirmed by measurement rather than taken on trust.
The old mutation flipped the final base64url CHARACTER of the sealed string.
With a 19-byte plaintext that character carries 2 significant bits plus 4 padding bits, so an `A` -> `B` flip can change only padding and decode to byte-identical ciphertext; GCM then verifies correctly and `open` correctly returns the plaintext.

Measured over 20000 seals with a probe using the real sealer:

```
old character-flip mutation, open() still succeeded: 5060/20000 = 25.30%
new byte-flip mutation,      open() still succeeded: 0/20000 = 0.00%
```

Fix: tamper at the BYTE level.
`withFlippedByte(sealed, index)` decodes the named component, flips a bit in byte 0 - always fully significant, whatever the plaintext length - and re-encodes.
Each tamper test also asserts the decoded bytes actually changed, so the mutation can never silently become a no-op again.
The helper carries the whole explanation in its doc comment, because the failure mode is not visible from the call site.

The same helper made two further cases cheap, so the file now pins all three sealed components: `refuses a tampered ciphertext`, `refuses a tampered auth tag`, `refuses a tampered iv`.
Suite went from 7 to 9 tests.
