## The final shape of `create()` - READ THIS, SLICE 06

```ts
async create(data: HubSessionRecord): Promise<string> {
  const id = newId();
  const now = this.#now().getTime();          // ONE clock read for both timestamps
  try {
    await this.#db.insert(hubBffSessions).values({
      id,
      hubRefreshTokenEnc: this.#sealer.seal(data.hubRefreshToken, id),
      accountId: data.accountId ?? null,
      expiresAt: new Date(now + SESSION_TTL_MS),
      absoluteExpiresAt: new Date(now + SESSION_ABSOLUTE_TTL_MS),
    });
  } catch (err) {
    throw this.#unavailable('hub session create failed', err);
  }
  return id;
}
```

Facts slice 06 depends on:

- **`create()` does NOT own a transaction.**
  It is a single `this.#db.insert(...)` on the pooled `getAdminDb()` connection - one statement, implicitly its own transaction, with no `db.transaction(...)` wrapper anywhere.
  Slice 06 wants the prior-session DELETE and this INSERT to commit or roll back together, so slice 06 has to introduce the `db.transaction(...)` itself.
  Its constraint-5 atomicity oracle (`keeps the prior session when the new insert fails`) is therefore genuinely load-bearing: there is nothing here for it to inherit.
- **`data.accountId` is honoured but is always `undefined` under 1.3.0.**
  `dist/server.js:407-413` is the only `store.create` call site in the bundle and passes exactly three keys, none of them `accountId`, so `account_id` is unconditionally `NULL`.
  This is the premise of slice 06's rescope and it is unchanged by this slice.
- **`absoluteExpiresAt` is written HERE and nowhere else in the file.**
  If slice 06 moves the insert inside a transaction, it must carry both timestamps and the single `now` read with it.
  Omitting `absoluteExpiresAt` is a compile error (the column is `NOT NULL` with no default and Drizzle's inferred insert type requires it), which is exactly why the column has no default.
- **A `create` failure still becomes `HubSessionStoreUnavailableError`**, so slice 06's transaction failure answers `503` through `hubBffErrorHandler` rather than a cookie-clearing `401`.
  Note that the SDK does NOT wrap `store.create` in a `try`, so the throw propagates to hono and reaches the router's `onError`.
- **`toSessionRecord(row, token)` is now the only place a Drizzle `Date` becomes an SDK ISO string.**
  Anything slice 06 adds that hands the SDK a record must go through it, not build the object inline.

## Standing risk, unchanged from the plan

The rolling-deploy window is real and accepted: an OLD replica still running the slice-01 `create` inserts without `absolute_expires_at`, which the new `NOT NULL` rejects, so a NEW login on an old replica fails for the overlap.
It surfaces as `hubBffErrorHandler`'s `503`, not a cookie-clearing `401`, so no existing session is harmed and the operator succeeds on retry.

The backfill's "logs nobody out" argument has a shelf life and it is written into the migration comment: it holds only while the oldest `hub_bff_sessions` row is under 90 days old.
`hub_bff_sessions` was created on 2026-08-03, so re-check before shipping if this run sits unshipped past 2026-11-01.
